Overview

How this document is structured, the layered approach, and the seven entities that make up the Consyst data model.

The layered approach

The data model is built in five layers, each confirmed before the next begins. This prevents the most common data modeling mistake — designing relationships before you fully understand the entities, or defining business logic before you know the shape of the data.

L1 ✓
Entities & fields
The things we store and what we know about each one. No relationships, no logic — just entities and their fields. Confirmed before proceeding.
L2
Relationships
How entities connect. Foreign keys, cardinality (one-to-many, many-to-many). Where ownership lives. Decisions that seem small but have large downstream implications.
L3
Business logic & calculations
Week score formula. Streak calculation. Grade thresholds. Consistency percentage. These are computed, not stored — but they must be defined precisely.
L4
Edge cases & constraints
What happens when a habit is archived mid-month? When a goal changes mid-week? When the user changes timezone? Stress-testing the model.
L5
Final review & documentation
Pull everything together. Check for gaps. Produce the clean, complete model ready for handoff to development.

Conventions used in this layer
C1
All entities have id, created_at, updated_at
Every entity has a primary key (id), a creation timestamp (created_at), and a last-updated timestamp (updated_at). These are not listed individually in each entity — they are assumed present on all tables.
C2
snake_case for all field names
All field names use snake_case convention (e.g. weekly_goal, created_at, habit_id). This is standard for SQL databases and most ORMs.
C3
Soft deletes via archived_at
Nothing is hard-deleted. Habits use archived_at to mark deactivation. This preserves historical data for Story and the life timeline. A null archived_at means the record is active.
C4
Dates are stored as DATE, timestamps as TIMESTAMPTZ
A habit log is associated with a calendar date (DATE), not a timestamp — because "did I exercise on Monday?" is a date question, not a time question. Authentication events and created_at fields use TIMESTAMPTZ (timestamp with timezone).

Relationship 1 — users → habits
FK
habits.user_id → users.id
Every habit belongs to exactly one user. A habit without a user cannot exist.
⚡
On user delete → cascade delete habits
If a user deletes their account, all their habits are deleted. This triggers cascade deletes down the chain — habit_logs, weekly_goals, and habit-linked milestones all go with the habits. This is the correct behaviour: the user has explicitly chosen to erase everything.
📌
Archived habits stay — they are not deleted
When a user archives a habit in the Habits screen, archived_at is set. The habit row stays. All its habit_logs stay. All its weekly_goals stay. The archived habit continues to appear in Story historical data and the life timeline. Only the user deleting their account removes it.
Relationship 2 — habits → habit_logs
FK
habit_logs.habit_id → habits.id
Every log entry belongs to exactly one habit. A log without a habit cannot exist.
🔑
Unique constraint: (habit_id, log_date)
One log per habit per calendar day. Enforced at the database level — not just the application level. This prevents duplicate check-ins if the user taps a checkbox twice quickly or if two requests race.
⚡
On habit delete → cascade delete logs
Only happens if the user deletes their account (which cascades from users → habits → habit_logs). Normal archiving does NOT delete logs — it just prevents new ones being created.
📌
Logs for archived habits are read-only history
Once a habit is archived, no new habit_logs can be created for it. Existing logs are preserved and remain queryable for Story, heatmaps, and exports. The application layer enforces this — archived habits do not appear in the check-in UI.
Relationship 3 — users → habit_logs (denormalised)

habit_logs carries both habit_id and user_id. The user could be reached via habit_logs → habits → users, but we store user_id directly on habit_logs. This is a deliberate denormalisation.

Why denormalise? The Now dashboard, the Pulse weekly grid, the Story heatmap, and the export feature all need to query "all check-ins for this user across a date range" — a very common, very frequent query. Without denormalisation it requires a JOIN through habits every time. With user_id on habit_logs, it's a direct index lookup on (user_id, log_date). The trade-off: we must ensure habit_logs.user_id always equals the user_id of the parent habit. This is enforced by only ever writing habit_logs through the application layer, never directly — and by a database trigger or check constraint if the team prefers belt-and-suspenders.

Relationship 4 — habits → weekly_goals (versioned)

This is the most query-critical relationship in the model. One habit can have many weekly_goals over its lifetime — one row per change. The question "what was the target for Exercise in Week 11?" is answered by finding the most recent weekly_goal row for that habit where week_start_date <= the Monday of Week 11.

FK
weekly_goals.habit_id → habits.id
Every goal version belongs to a specific habit.
🔑
Unique constraint: (habit_id, week_start_date)
One goal record per habit per week start date. Prevents duplicate entries for the same week.
📋
How to find the active goal for a given week
Query: SELECT target_days FROM weekly_goals WHERE habit_id = ? AND week_start_date <= [target_monday] ORDER BY week_start_date DESC LIMIT 1. This returns the most recent goal that was in effect on or before the week in question. If no row exists, fall back to habits.default_weekly_goal.
⚡
Goal changes take effect the following Monday
When a user changes a goal, a new weekly_goals row is inserted with week_start_date = next Monday. The current week is never mid-stream altered — the design decision from Layer 1 is enforced here at the relationship level. The Settings screen shows "changes take effect from the start of next week."
⚡
On habit delete → cascade delete weekly_goals
Only on full account deletion. Archiving preserves weekly_goals for historical score calculations.

The versioned goal design means the week score for any past week can always be recalculated accurately — even years later. The denominator (total possible check-ins) is derived from the goal that was active that week, not the current goal. This is what makes the Story consistency trend trustworthy over time.

Relationship 5 — users → day_notes
FK
day_notes.user_id → users.id
Every day note belongs to exactly one user.
🔑
Unique constraint: (user_id, note_date)
One note per user per calendar day. The UI allows editing the same note — saving overwrites the existing row (UPDATE), not inserts a new one (INSERT).
⚡
On user delete → cascade delete day_notes
Day notes are personal data — they go with the user on account deletion.
Relationship 6 — users → reflections
FK
reflections.user_id → users.id
Every reflection belongs to exactly one user.
🔑
Unique constraint: (user_id, reflection_month)
One reflection record per user per month. The four cards in the Reflect section (wins, gaps, journal, intentions) are four fields on the same row — not four separate records. Saving any card updates the single reflection row for that month.
📋
Upsert pattern — create if not exists, update if exists
When the user saves anything in Reflect for March, the application does: INSERT INTO reflections (...) ON CONFLICT (user_id, reflection_month) DO UPDATE SET [field] = [value], updated_at = NOW(). This handles both the first save and subsequent edits cleanly without needing to check for existence first.
⚡
On user delete → cascade delete reflections
Personal journal data — gone on account deletion.
Relationship 7 — users → milestones and habits → milestones
FK
milestones.user_id → users.id (required)
Every milestone belongs to a user. Always populated.
FK
milestones.habit_id → habits.id (optional)
Nullable. A streak milestone references the specific habit. A "first A-grade week" or "Day 1" milestone is system-wide — habit_id is null.
📌
On habit archive → milestones are NOT deleted
A milestone is a historical record. If the user archives Exercise, their "14-day streak on Exercise" milestone remains intact in the timeline. The milestone's habit_id still points to the archived habit row — and because we soft-delete (archive, not delete), the join still resolves. The application can show the habit name from the archived record.
⚡
On habit hard delete (account deletion) → SET NULL on milestones.habit_id
If a user deletes their account and the habit rows are cascade-deleted, milestones.habit_id is SET NULL rather than cascade-deleting the milestones themselves. This is the one case where we prefer SET NULL over CASCADE — because milestones belong to the user, not the habit. The milestone survives; it just loses its habit reference.
⚡
On user delete → cascade delete milestones
The user is gone — all their milestones go with them.

Layer 3 — Business Logic

Every calculation the system performs. These are not stored values — they are computed on demand from the raw data in Layers 1 and 2. Defined precisely so any developer can implement them identically.

✓ Complete · confirmed March 2026
Calculation 1 — Today's progress

Shown on the Now dashboard score card and the top bar streak pill. The simplest calculation in the system.

-- Today's progress --

today_completed =
  COUNT of habit_logs
  WHERE user_id = :user_id
    AND log_date = :today          -- user's local date
    AND completed = true

today_total =
  COUNT of habits
  WHERE user_id = :user_id
    AND archived_at IS NULL        -- active habits only

today_progress = today_completed / today_total

-- Display: "2/5" (fraction, not percentage)
-- If today_total = 0 (no habits): show empty state, not 0/0

Today's progress is a count of active habits completed today — it is not weighted by each habit's weekly goal. If you have 5 habits and complete 2, the score is 2/5 regardless of whether those habits had a goal of 7× or 1×. This matches exactly what the Now check-in widget shows.

Calculation 2 — Week score

The core metric of the app. Shown on Now, Pulse score cards, Story monthly summary, and used as the basis for the grade. This is where the versioned weekly_goals table earns its complexity.

-- Week score for a given week (identified by its Monday date) --

-- Step 1: Get active habits for this user --
active_habits = habits WHERE user_id = :user_id AND (
  archived_at IS NULL                          -- currently active
  OR archived_at > :week_start_date            -- archived after this week started
)
-- Only include habits that existed during this week
-- A habit created after this week ends is excluded
-- A habit archived during this week is still included (pro-rated in edge cases)

-- Step 2: For each habit, find the active weekly goal --
get_goal(habit_id, week_start_date):
  SELECT target_days FROM weekly_goals
  WHERE habit_id = :habit_id
    AND week_start_date <= :week_start_date
  ORDER BY week_start_date DESC
  LIMIT 1
  -- Fallback if no weekly_goal row exists yet:
  -- use habits.default_weekly_goal

-- Step 3: Build the denominator (total possible completions) --
week_target =
  SUM of get_goal(habit.id, week_start_date)
  FOR EACH habit IN active_habits

-- Step 4: Build the numerator (actual completions) --
week_completed =
  COUNT of habit_logs
  WHERE user_id = :user_id
    AND log_date BETWEEN :week_start_date AND :week_end_date
    AND completed = true
    AND habit_id IN (active_habits.ids)

-- Step 5: Calculate the score --
week_score = ROUND((week_completed / week_target) * 100, 1)

-- Edge: week_target = 0 → return null (no habits configured)
-- Score can exceed 100% if user completes more than their target
-- Cap display at 100% but store raw value for "133%" achievements in Now
-- Week boundaries: Monday 00:00:00 → Sunday 23:59:59 in user's timezone

The week score can technically exceed 100% — if a user's Exercise goal is 3× but they complete it 4 times, that habit contributes 4/3 = 133% to their score. The design shows this as "133%" in the Top Performer widget on Now. The overall week score is capped at 100% for display purposes in the grade card and score card — but the raw value is preserved for the "exceeded goal" display in the Pulse habit table.

Calculation 3 — Weekly grade

Applied to the week score to produce the A/B/C grade shown on the Pulse grade card and in the Story monthly summary badges.

-- Weekly grade thresholds --

get_grade(week_score):
  IF week_score >= 85.0  → "A"
  IF week_score >= 70.0  → "B"
  ELSE                  → "C"

-- Grade message (forward-looking, used in Pulse grade card) --
get_grade_message(week_score, days_remaining_in_week):

  IF grade = "A":
    "Excellent week. Your system is running well."

  IF grade = "B" AND days_remaining > 0:
    points_to_a = CEIL((85 - week_score) * week_target / 100)
    "You're doing well — {points_to_a} more check-in(s) today for an A."

  IF grade = "C" AND days_remaining = 0:

Calculation 4 — Streak

The most complex calculation in the system. A streak is the number of consecutive calendar days on which a habit was completed, counting backwards from the most recent completed day.

-- Streak calculation for a single habit --

get_streak(habit_id, reference_date):
  -- reference_date is today in the user's local timezone
  -- We look backwards from yesterday (today is pending)

  -- Step 1: Get all completed log dates for this habit, newest first --
  logs = SELECT log_date FROM habit_logs
    WHERE habit_id = :habit_id
      AND completed = true
    ORDER BY log_date DESC

  -- Step 2: Determine the starting point --
  check_date = reference_date - 1 day  -- start from yesterday

  -- Exception: if today is already completed, start from today --
  IF reference_date IN logs:
    check_date = reference_date

  -- Step 3: Walk backwards, counting consecutive completed days --
  streak = 0
  WHILE check_date IN logs:
    streak += 1
    check_date = check_date - 1 day

  RETURN streak

-- Key rules: --
-- A gap of even one day breaks the streak (streak resets to 0)
-- Today counts toward the streak only if completed
-- Today does NOT break the streak if not yet completed (it's pending)
-- Yesterday not completed = streak is 0 (broken), not pending
-- Streak is per-habit, not global
-- "14 day streak" means the habit was completed on 14 consecutive calendar days

-- Longest active streak (shown on Now score card) --
longest_active_streak =
  MAX(get_streak(habit.id, today))
  FOR EACH active habit
  WHERE get_streak(habit.id, today) > 0

The "today is pending" rule is the most important nuance. If today is Monday and I haven't checked in yet, my streak is calculated from Sunday backwards — today doesn't break it, but it also doesn't count yet. This means the streak number in the top bar can increase mid-day once the user checks off today's habit. This matches the design — the streak pill on Now updates live as the user checks in.

Calculation 5 — Monthly consistency

The per-habit percentage shown in the Story monthly heatmap, the monthly summary badges (Best/Strong/Good/Watch), and the Goal vs Actual widget.

-- Monthly consistency for one habit in one month --

get_monthly_consistency(habit_id, year, month):

  -- Step 1: Get every Monday (week_start) within the month --
  weeks_in_month = all Mondays where the week overlaps with [year, month]
  -- A week "overlaps" if any day of that Mon–Sun falls in the month
  -- A week that starts in February and ends in March is counted in both months
  -- but only the days within the target month contribute to the score

  -- Step 2: For each week, get the active goal --
  -- Pro-rate for partial weeks at month boundaries --
  monthly_target = 0
  FOR EACH week IN weeks_in_month:
    goal = get_goal(habit_id, week.monday)
    days_in_month = COUNT days of this week that fall within [year, month]
    -- Full week: days_in_month = 7, contribute full goal
    -- Partial week: pro-rate proportionally
    monthly_target += goal * (days_in_month / 7)

  monthly_target = ROUND(monthly_target)  -- round to nearest integer

  -- Step 3: Count actual completions in the month --
  monthly_completed =
    COUNT habit_logs
    WHERE habit_id = :habit_id
      AND log_date BETWEEN first_day_of_month AND last_day_of_month
      AND completed = true

  -- Step 4: Calculate consistency --
  consistency = ROUND((monthly_completed / monthly_target) * 100, 1)

  RETURN consistency

-- Heatmap colour thresholds (Story intensity heatmap) --
heatmap_colour(consistency):
  IF consistency >= 70  → green   (#DCFCE7 bg, #166534 text)
  IF consistency >= 40  → amber   (#FEF9C3 bg, #854D0E text)
  ELSE               → grey    (#F1F5F9 bg, #94A3B8 text)

-- Monthly habit summary badge thresholds (Story monthly summary) --
summary_badge(consistency):
  IF consistency >= 90  → "Best"
  IF consistency >= 75  → "Strong"
  IF consistency >= 60  → "Good"
  ELSE               → "Watch"
Calculation 6 — Month score

The overall monthly score shown on the Story score card — the single number summarising the whole month. It is the average of all weekly scores within the month, not the monthly consistency of individual habits.

-- Month score --

get_month_score(user_id, year, month):

  weeks = all weeks that overlap with [year, month]

  weekly_scores = []
  FOR EACH week IN weeks:
    score = get_week_score(user_id, week.monday)
    IF score IS NOT NULL:          -- skip weeks before the user started
      weekly_scores.append(score)

  IF weekly_scores is empty:
    RETURN null                    -- no data yet

  RETURN ROUND(AVG(weekly_scores), 1)

-- Why average of week scores rather than raw completions/targets? --
-- Because it matches what the user already sees week by week in Pulse.
-- A month score of 78% means "your average Pulse week this month was 78%".
-- This is more intuitive than a raw ratio across all 4+ weeks.

Calculation 8 — Consyst observation logic

The "Consyst notices" widget on Now and the "Consyst surfaces" card in Reflect. These are not stored calculations — they are generated on demand when the user opens the relevant screen. The system runs a set of pattern checks against the user's data and returns the most relevant observation.

-- Consyst observation candidates (evaluated in priority order) --
-- Returns the single highest-priority observation to show --

get_observation(user_id, context):
  -- context = "now" (dashboard) or "reflect" (journal)

  candidates = []

  -- Pattern 1: Active streak milestone approaching --
  FOR EACH habit in active_habits:
    streak = get_streak(habit.id, today)
    next_milestone = next value in [7,14,21,30,60,90,180,365] above streak
    IF next_milestone - streak <= 2:
      candidates.add(priority=1,
        "{habit.name} is {streak} days in — {next_milestone - streak} more day(s) to a milestone.")

  -- Pattern 2: Habit slipping — below 50% of weekly goal with 2+ days left --
  FOR EACH habit in active_habits:
    days_completed_this_week = COUNT logs this week for habit
    current_goal = get_goal(habit.id, this_week_monday)
    days_left_in_week = days until Sunday
    IF days_completed_this_week / current_goal < 0.5 AND days_left_in_week >= 2:
      candidates.add(priority=2,
        "{habit.name} is behind this week — {current_goal - days_completed_this_week} needed in {days_left_in_week} days.")

  -- Pattern 3: Top performing habit this week --
  best_habit = habit with highest (completed / goal) ratio this week
  IF best_habit.ratio >= 1.0:
    candidates.add(priority=3,
      "{best_habit.name} has already hit its weekly goal. Strong week.")

  -- Pattern 4: Week score improvement --
  this_week = get_week_score(user_id, this_monday)
  last_week = get_week_score(user_id, last_monday)
  IF this_week > last_week AND this_week - last_week >= 8:
    candidates.add(priority=3,
      "Up {this_week - last_week} points on last week. The system is working.")

  -- Pattern 5: Day-of-week slip pattern (requires 4+ weeks of data) --
  IF user has >= 4 weeks of data:
    today_of_week = day name (e.g. "Sunday")
    slip_rate = % of [today_of_week] days where habit was NOT completed, last 4 weeks
    worst_habit_today = habit with highest slip_rate on today_of_week
    IF worst_habit_today.slip_rate >= 0.75:
      candidates.add(priority=2,
        "{worst_habit_today.name} tends to slip on {today_of_week}s. Good day to break that.")

  -- Return highest priority candidate (lowest priority number) --
  -- If no candidates: return null (widget hidden, not shown as empty) --
  RETURN candidates.sort_by(priority).first()

Performance notes — what to cache
P1
Week score — compute on demand, consider caching after week closes
During an active week, week score changes with every check-in — don't cache it. Once a week is closed (Sunday passes), the score is immutable. A background job can compute and store the final week score in a cached_week_scores table to avoid recalculating it every time Story or the past-weeks archive is loaded.
P2
Streak — compute on demand
Streak changes with every check-in and every new day. Always computed fresh. With the (habit_id, log_date DESC) index from Layer 2, this is a fast sequential scan on a small set of rows — no caching needed.
P3
Monthly consistency — compute on demand for current month, cache past months
Like week scores, past months are immutable. A background job after each month closes can cache the monthly consistency per habit in a cached_monthly_stats table. Current month is always computed fresh.
P4
Consyst observation — compute on page load, no cache
Observations are contextual and change frequently. Always compute fresh on each Now or Reflect load. The query set is bounded (limited to current week's data) so it's fast without caching.

Layer 4 — Edge Cases & Constraints

Every situation where the model needs a defined rule to behave consistently. Undefined edge cases become developer guesswork — which means inconsistent behaviour. Each case here has exactly one correct answer.

✓ Complete · confirmed March 2026
Theme 1 — Habit archived mid-week

Situation: The user archives Exercise on Wednesday. The week started Monday. Exercise had a goal of 3× and was completed Monday and Tuesday.

E1.1
Include the archived habit in the current week's score
The habit was active at the start of the week. Its Monday and Tuesday completions happened legitimately. Its goal applies to the days it was active. The week score denominator includes Exercise's target for the days it was active (Mon–Tue = 2 days, goal = 3×, pro-rated contribution = 2/7 × 3 = ~0.86). The numerator includes its 2 completions. Archiving mid-week does not retroactively remove the habit from the current week's score.
E1.2
Archived habits are excluded from all future weeks immediately
From Thursday onwards (the day after archiving), Exercise does not appear in the check-in list, does not contribute to the weekly target denominator, and cannot receive new habit_logs. The week score from Thursday through Sunday is calculated without Exercise in scope.
E1.3
Implementation rule for week score with mid-week archive
In the get_week_score calculation, include a habit if: (a) it was active on the Monday of the week (archived_at IS NULL OR archived_at > week_start_date), AND (b) it was created on or before the Sunday of the week (created_at <= week_end_date). The denominator uses the full weekly goal even for archived habits — pro-rating by day of archive adds complexity without meaningful accuracy gain for a 7-day window.

Decision: use full goal in denominator even for a mid-week archive. If Exercise had a 3× goal and the user archived it Wednesday after completing it Monday and Tuesday (2/3), the week score reflects that slight shortfall — which is correct. The user chose to archive mid-week; the score reflects their week honestly.

Theme 2 — Habit archived mid-month

Situation: The user archives Meditation on March 15. The month has 31 days. Meditation had a goal of 5× per week.

E2.1
Monthly consistency uses the days the habit was active
For the Story heatmap and monthly summary, Meditation's monthly target is pro-rated to the days it was active. It was active for 15 of 31 days. The monthly target = SUM of weekly goal contributions for each week, counting only days where the habit was active. Weeks that fall entirely before March 15 contribute their full weekly goal. The week containing March 15 contributes a partial goal. Weeks after March 15 contribute zero.
E2.2
Archived habits still appear in Story historical view
In the Story monthly view for March, Meditation appears in the heatmap and monthly summary — labelled with a subtle "archived" indicator. Its consistency is calculated against its pro-rated target. In April and beyond, it does not appear in the active habit list but its March data remains in the Story archive.
E2.3
Month score is unaffected by mid-month archive
The month score (average of weekly scores) already handles this correctly via E1.2 and E1.3 — each week score includes the habit only for the days it was active. No special handling needed at the month score level.
Theme 3 — Goal change mid-week

Situation: It is Wednesday. The user changes their Reading goal from 5× to 3× per week. The current week started Monday.

E3.1
Goal changes always take effect the following Monday
When the user saves a new goal, the application inserts a new weekly_goals row with week_start_date = next Monday. The current week's score continues to use the old goal (3× in this case is the new goal — but the current week uses the 5× goal that was set at the start of the week). This is enforced at the application layer, not the database layer.
E3.2
The UI communicates this clearly
When the user saves a goal change, the Habits modal shows a confirmation: "New goal takes effect from Monday, [date]." The current week's Pulse grid continues to show the old target. This prevents confusion when the user sees their score calculated against a goal they thought they changed.
E3.3
Exception — first goal set on a habit
When a user creates a new habit, the first weekly_goals row is inserted with week_start_date = the Monday of the current week (not next Monday). This means the habit participates in the current week's score immediately from the day it was created. The denominator is pro-rated for the remaining days of the week — if created on Wednesday with a 3× goal, the denominator contribution for this week is approximately 3 × (5/7) ≈ 2.1, rounded to 2.
Theme 4 — Habit added mid-week

Situation: The user adds a new habit (Running, 3× per week) on Thursday of an ongoing week.

E4.1
New habits participate in the current week immediately
Running appears in the Now check-in list immediately. Its goal is pro-rated for the remaining days of the week (Thu–Sun = 4 days, goal = 3×, pro-rated = 3 × 4/7 ≈ 1.7, rounded to 2). The denominator for this week increases by 2. The user can check off Running on Thursday, Friday, Saturday, and Sunday.
E4.2
No retroactive check-ins for days before creation
Running cannot be checked off for Monday, Tuesday, or Wednesday — those days predate the habit's creation. The Pulse grid shows the habit starting from Thursday, with Mon–Wed cells empty and locked. The user cannot backdate check-ins for a habit to before it existed.
E4.3
From next week onwards, Running participates at full goal
The weekly_goals row inserted on creation has week_start_date = this Monday (current week). Next week, the same row applies with its full 3× target across all 7 days — no pro-rating needed for complete weeks.
Theme 5 — Timezone changes

Situation: The user moves from New York (UTC-5) to London (UTC+0). They update their timezone in Settings on March 15.

E5.1
All past habit_logs are stored as DATE — they are timezone-agnostic
A habit_log with log_date = 2026-03-10 means "I completed this on March 10th." It does not record a timestamp — just a date. This date was correct for the user's timezone at the time of logging. Changing timezone does not alter past log_date values. Past data is unaffected.
E5.2
New check-ins use the updated timezone immediately
From the moment the user saves their new timezone in Settings, all subsequent check-ins use the new timezone to determine today's date. If it is 11pm in New York (which is 4am the next day in London), after the timezone change "today" becomes the next calendar day.
E5.3
Streak calculation uses the current timezone
Streak always walks backwards from today in the user's current timezone. If a timezone change means "today" is now March 16 instead of March 15, the streak calculation starts from March 16. This could theoretically skip a date in the streak walk — which the system treats as a broken streak for that transition day. This is the accepted trade-off: timezone changes are rare, and the streak accurately reflects the user's current timezone going forward. A milestone record in the system history log notes the timezone change date.
E5.4
Timezone is stored on the user record, applied at read time
The application converts all date-sensitive queries to the user's timezone at query time. The database stores DATE values neutrally. The conversion happens in the application layer: "today" = current UTC timestamp converted to users.timezone → extract date portion.
Theme 6 — Streak edge cases
E6.1
Day 1 streak
If a user completes a habit for the very first time today, their streak is 1. Yesterday has no log (the habit didn't exist or wasn't completed), so the backwards walk stops immediately after counting today. Streak = 1 is correct — they have a 1-day streak starting today.
E6.2
Habit existed but was never checked — streak is 0
If a habit exists but the user has never completed it (no completed habit_logs), the streak is 0. This is the correct display for a habit that has been added but not yet started.
E6.3
User unchecks today's completed habit
If today was completed and the user unchecks it (setting completed = false), the streak recalculates from yesterday. If yesterday was completed, the streak still shows that count — today is now pending again, not broken. The streak reflects the last confirmed completed day.
E6.4
Midnight boundary — check-in at 11:59pm
A check-in at 11:59pm creates a habit_log with log_date = today (in the user's timezone). At 12:00am the next day, "today" becomes tomorrow. The streak walk starts from yesterday (the 11:59pm check-in date), correctly counting it. No race condition — the log_date is determined at write time and stored permanently.
E6.5
No backdating allowed
Users cannot log a check-in for a date in the past. The application enforces: log_date must equal today in the user's timezone. This prevents streak manipulation and keeps the data honest. The one exception: if a bug caused a missed log, an admin can backdate — but no user-facing UI exposes this.
E6.6
No future dating allowed
Similarly, log_date cannot be in the future. Enforced at the application layer with a constraint: log_date <= today in the user's timezone. A database check constraint provides belt-and-suspenders enforcement.
Theme 7 — Data integrity constraints
E7.1
Check-in on an archived habit — blocked
The application layer prevents creating a habit_log for a habit where archived_at IS NOT NULL. If somehow a request slips through (race condition, direct API call), a database trigger or check constraint rejects it: CONSTRAINT check_habit_not_archived CHECK that the referenced habit's archived_at IS NULL at the time of INSERT.
E7.2
Duplicate check-in on same habit + date — upsert, not error
The UNIQUE(habit_id, log_date) constraint means two INSERT attempts for the same habit and date will conflict. The application handles this with an upsert: INSERT ... ON CONFLICT (habit_id, log_date) DO UPDATE SET completed = :new_value, updated_at = NOW(). The user tapping a checkbox twice quickly results in the second tap toggling the existing record — not an error.
E7.3
habit_logs.user_id drift — cross-user log impossible
Because user_id is denormalised on habit_logs, there is a theoretical risk of a log's user_id not matching its parent habit's user_id. This is prevented by: (a) only writing habit_logs through the application layer which always sets user_id from the authenticated session, never from user input, and (b) a database trigger that validates habit_logs.user_id = habits.user_id on every INSERT.
E7.4
WeeklyGoal week_start_date must always be a Monday
The week_start_date field is only valid if it is a Monday. The application always computes week_start_date as the Monday of the current or next week. A database check constraint enforces this: EXTRACT(DOW FROM week_start_date) = 1 (Monday in ISO week numbering). This prevents any invalid goal rows from entering the system.
E7.5
reflection_month must always be the first of the month
reflection_month is stored as the first day of the month (e.g. 2026-03-01). A database check constraint enforces: EXTRACT(DAY FROM reflection_month) = 1. This prevents partial-month keys and ensures consistent querying.
E7.6
target_days must be between 1 and 7
A weekly goal of 0 days is meaningless (why track a habit you never intend to do?) and a goal of more than 7 is impossible. Database check constraint: target_days BETWEEN 1 AND 7. The day-pip selector in the UI also enforces this — you cannot deselect all days.

Same email via Google and email/password
Flagged in Layer 1. Resolution: if a user signs up with Google using [email protected], a users row is created with google_id populated and password_hash null. If the same person later tries to sign up with email/password using [email protected], the system detects the email collision and responds: "An account with this email already exists. Theme 9 — Score and calculation edge cases
E9.1
Week score with zero habits
If a user has no active habits, week_target = 0. Division by zero is prevented by returning null rather than 0%. The UI shows the empty state — the score card displays "—" rather than 0%. This matches the Day 1 empty state design exactly.
E9.2
Week score exceeding 100%
Defined in Layer 3. Raw value is stored and used in the Top Performer widget. Display is capped at 100% in the score card and grade card. No special handling needed — the data is correct, only the display clips it.
E9.3
Month score for a month with no completed weeks
If the user had habits but completed zero check-ins in a month, weekly_scores will be a list of 0.0 values. AVG([0,0,0,0]) = 0.0 — month score is 0%. This is correct and different from the null returned when there are no habits (E9.1). Zero means "you had habits but didn't complete any." Null means "you had no habits to track."
E9.4
Consistency percentage for a newly added habit mid-month
A habit added on March 20 has a monthly target pro-rated to March 20–31 only (12 days). Its consistency is calculated against that pro-rated target — not the full month. This is correct and prevents a newly added habit from automatically showing a low consistency score for the days before it existed.
E9.5
Grade message when days_remaining calculation yields 0 check-ins needed
If a user is at 84.9% and needs only 0.1 more percentage points to reach an A — which rounds to 0 additional check-ins — the message should not say "0 more check-ins for an A." The application floors the check-ins needed at 1 in the message: IF CEIL(points_needed × week_target / 100) = 0 THEN show "Almost there — finish strong today."
E9.6
Milestone duplicate detection across streak resets
If a user achieves a 7-day streak, breaks it, and then achieves a 7-day streak again — should a second "7-day streak" milestone be created? Yes. The duplicate check in Layer 3 (C7) uses the metadata.streak_length field but does not prevent a second milestone of the same type if the first streak was broken and rebuilt. The milestone type is streak_record, and each achievement of that milestone is worth recording. The life timeline shows both, separated by the reset date.
Theme 10 — First week of system

Situation: The user's system_started_at is March 4 (a Wednesday). Their first week in Consyst is a partial week — Wednesday through Sunday only.

E10.1
First week is always partial — treat it like any mid-week habit addition
The week of March 2 (Mon–Sun) started before the user existed. The user's first participation is from March 4. The week score for that week is calculated from March 4 onwards only — habits are pro-rated for the days remaining in the week (Wed–Sun = 5 days). The Pulse grid shows Mon–Tue cells as locked/empty for all habits.
E10.2
Story monthly view for the first month
In Story, the first month shows only the weeks the user was active. Weeks before system_started_at are excluded from the month score average and from the heatmap. The heatmap cells for those weeks show as "not applicable" (no color, no percentage) rather than grey — grey means tracked but low, which is different from "not yet started."
E10.3
Consistency trend starts from the first full or partial week
The consistency trend chart in Story shows all weeks from system_started_at onwards. The first week may have a lower score due to being partial — this is expected and the user is not penalised for it in the monthly summary. Week 1 is always shown, even if it is a 2-day partial week.

Design decisions — complete record

Every significant decision made during the data model build, in one place for reference.

D1
UUID primary keys on all tables
No sequential integer IDs exposed in URLs or API responses. UUIDs are generated database-side with gen_random_uuid().
D2
Soft deletes via archived_at (habits) and suspended_at (users)
Nothing is hard-deleted during normal operation. Habits are archived, not deleted. User accounts are suspended, not deleted. Data is preserved for historical accuracy. Hard deletes only happen on explicit account deletion requests, which cascade everything.
D3
Dates stored as DATE, timestamps as TIMESTAMPTZ
Check-ins are date events, not time events. habit_logs.log_date, weekly_goals.week_start_date, milestones.milestone_date, day_notes.note_date, reflections.reflection_month are all DATE. Created/updated fields are TIMESTAMPTZ.
D4
user_id denormalised on habit_logs and weekly_goals
Trades slight normalisation purity for significant query performance on the most frequent read paths. A trigger enforces consistency — habit_logs.user_id must always match its parent habit's user_id.
D5
WeeklyGoal is versioned — goals are never altered, only superseded
Each goal change inserts a new row with the next Monday as week_start_date. The previous row is never touched. Historical week scores are always accurately recalculable against the goal that was active at the time.
D6
JSONB for wins, gaps, intentions in reflections
Avoids separate junction tables for simple ordered string arrays. JSONB allows future metadata per item (date added, emoji, etc.) without schema changes. No querying within these arrays is required — they are always retrieved as complete arrays.
D7
milestones.habit_id is SET NULL on habit delete, not CASCADE
A milestone is a historical record belonging to the user, not the habit. It survives habit deletion. The habit name is stored in the milestone title at creation time, so the record remains meaningful even after habit_id becomes null.
D8
No caching tables in schema — caching is application-layer
Past week scores and past monthly consistency values are immutable once the period closes and can be cached in application memory or a Redis layer. The database schema stays clean — no cached_scores or cached_stats tables. This decision can be revisited if query performance becomes a problem at scale.
D9
Admin roles are minimal for v1 — three fields only
role (user/admin), suspended_at, is_test. No audit log, no permission scopes, no multi-level hierarchy. The admin for v1 is one person with full database access. Role-based complexity is deferred until there is a real operational need — i.e. a team with different access levels.
D10
No backdating or future-dating of check-ins
log_date must equal today in the user's timezone. Enforced at application layer and by a CHECK constraint. Streak integrity depends on this — allowing backdating would make the streak calculation unreliable and gameable.
D11
Goal changes take effect next Monday — never mid-week
Preserves the integrity of the current week's score. The user made a commitment at the start of the week under the existing goal. Mid-week changes are deferred to create a clean, predictable system. The UI communicates the effective date explicitly.
D12
Same email cannot exist across Google and email/password auth
The UNIQUE constraint on users.email enforces this at the database level. Account linking (connecting both methods to one account) is a future feature, not a v1 requirement.
What this model does not include — and why
—
No social or sharing features
No friends, followers, shared habits, or public profiles. Consyst is a private personal OS. All data is private to the user. This is a design decision, not an oversight.
—
No notifications table
Notification preferences (reminder times, toggles) are stored in Settings — but as separate fields on the users table or a companion user_preferences table, not a notifications log. Actual notification delivery is handled by a third-party service (e.g. email provider, push service). No notification history is stored in this schema.
—
No billing or subscription table
Consyst's pricing model has not been decided. If a subscription tier is introduced, a subscriptions table will be added. For v1, all users have equal access — no gating needed in the schema.
—
No cached or materialised score tables
All scores are computed from raw data. If performance becomes a problem at scale, a caching layer (application or Redis) handles past periods. The schema stays clean and all calculations remain derivable from source data.
—
No audit log table
Admin actions are not logged in the database for v1. At the scale and team size of initial launch, this is not needed. If regulatory requirements or team size make it necessary, an admin_audit_log table is a straightforward addition.
