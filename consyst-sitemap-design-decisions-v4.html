01
Design Philosophy

The principles that govern every decision in Consyst — from the largest structural choice to the smallest label.

Core idea

Consyst is not a productivity app. It is a personal operating system — infrastructure that runs quietly in the background of a life. Where most habit apps compete for attention, Consyst earns trust by being consistently present and precisely useful.

The single rule that drives every decision: the system should feel more intelligent than the interface looks. Complexity belongs in the logic. Simplicity belongs on the surface.

"You don't use Consyst. You run on it." — The interface should feel inevitable, not designed. Every screen earns its place or doesn't exist.

Design principles
P1
Ultra-minimalist first, open up gradually
The app starts as simple as possible and opens up as the user builds familiarity. Nothing is shown before it's needed. The interface earns complexity — it doesn't start with it.
P2
Companion over coach
Consyst observes and reflects — it never instructs or pressures. The tone is warm and precise. A quiet presence that's been paying attention, not a drill sergeant counting failures.
P3
Sections not pages — score cards not screens
Most information lives as inline widgets within a section, not as separate navigable destinations. A user should be able to understand the entire app by reading the sidebar once.
P4
No sub-navigation anywhere
There are no tabs, no secondary nav bars, no internal page switching within any section. Each section is one scrollable surface. Complexity is expressed through layout and widgets — never through navigation layers.
P5
Light mode only — one consistent theme
The entire application uses a single warm light theme. No dark mode, no toggle. Tonal consistency reinforces the feeling that everything belongs to the same unified system.
P6
Brand colors as the only accent layer
Coral, amber, teal, blue, and purple carry semantic meaning and appear consistently in that role. They are the only chromatic elements beyond neutrals. Each section has its own color — the user learns the language quickly.
P7
Web-first, mobile-responsive
Designed as a web application. The desktop viewport is the primary surface. Mobile adapts from it — it doesn't drive it. This gives the design room to breathe and makes the OS metaphor feel grounded.
P8
Gentle grading — honest but never punitive
The A/B/C grading system in Pulse uses positive framing at every threshold. A user should know they're behind — but they should also know exactly what it takes to get back on track. The message is always delivered with care.
P9
Habits management is a core action, not a settings concern
The ability to add and edit habits is a primary function of the app — not an administrative task buried in settings. Habits lives in the main sidebar navigation at the same level as Today and Progress.
02
Naming System

Every section name was chosen to describe the emotional experience of being there — not what the screen contains.

The naming philosophy

The words dashboard, weekly, monthly, habits, and reflection are functional descriptions. They tell you what a screen contains. Consyst is a companion — the navigation should speak the companion's language. Each name is a feeling, not a category.

Final section names
Now
The dashboard — your current state
Not "Dashboard" — that's a tool word. "Now" is a time word. It says: this is where you are right now. Score cards, today's progress, top performer, what needs a push, this week at a glance. Everything you need to orient yourself in under five seconds.
Pulse
The weekly view — your rhythm
Not "Weekly" — that's a calendar word. "Pulse" is a vital-signs word. It says: is the system alive and healthy? The weekly grid, checkboxes, score, grade, and progress per habit. The mid-game view. Check it a few times a week.
Story
The monthly view — your arc
Not "Monthly" — that's an accounting word. "Story" is a narrative word. It says: this is the chapter you're writing. Score cards, goal vs actual, intensity heatmap, consistency trend, monthly summary. This is where the magic happens — designed to feel motivating, not analytical.
Habits
The setup layer — your system
"Habits" is the one functional name kept deliberately — because it's the most important thing in the app and should be completely unambiguous. Add, edit, archive habits via modal popup. Set weekly goals with day-pip selectors. This is the infrastructure of your personal OS.
Reflect
The journal — your inner voice
Not "Journal" or "Reflection" — "Reflect" is a verb. It says: come here to think. Monthly wins, gaps and risks, notes and journal, next month intentions. The calmest screen in the app. Designed to feel like a private space, not a form.
Settings — not a section

Settings is accessed via a gear icon at the bottom of the sidebar — never as a primary navigation item. Account preferences, reminders, profile, and data export all live here. It should feel like opening the back panel of a well-built machine: rarely needed, precise, and clean.

04
Section Breakdown

The emotional job, design intent, and key rules for each of the five sections.

Now — dashboard

Emotional job: Orient. Before anything else, the user should know the state of their system in under 5 seconds.

Design intent: A single fixed-height screen — nothing scrolls. Four score cards (week score, today, longest streak, active habits) communicate the state at a glance. The middle row is three widgets: today's live check-in, top performer, and what needs a push. The bottom row shows the week in miniature and one Consyst observation. The 3×2 grid layout ensures every element is visible without any scrolling or clicking.

Key rule: Now is a glance, not a dashboard. The user should never need to read — only scan.

Pulse — weekly

Emotional job: Assess. Is this week going well? Where is it slipping? Is there still time to fix it?

Design intent: The habit × day grid is the hero. Score cards at the top communicate the state. The grade card is the centrepiece — it uses a large letter grade, a forward-looking message, and a threshold bar. The message is always constructive: if you're at a B, it tells you exactly what it takes to reach an A. The grid below allows checking and unchecking — this is the only place in the app where the user logs weekly completions. Each habit row shows a progress bar and streak.

Key rule: Users can only check/uncheck weekly achievements in Pulse — they cannot add or edit habits here.

The grade system: A = 85%+, B = 70%+, C = below 70%. Every grade message is written to be honest but kind. A C says "you're behind — but here's exactly how to get back." The user should feel nudged, never shamed.

Story — monthly

Emotional job: Feel something. Pride, perspective, momentum. This is the reward for showing up daily — and it should feel like one.

Design intent: Story is designed to feel magical. A month picker at the top, four score cards, then two side-by-side widgets: Goal vs Actual shows the gap between intention and reality as horizontal bars. The Intensity Heatmap shows habits × weeks as a grid of colored cells — green for strong weeks, amber for close, grey for low. This is where you can see at a glance whether things are happening or not happening. Below that, the Consistency Trend chart and the Monthly Habit Summary ranked list.

Key rule: Story should reward the user who has been consistent. It makes long-term commitment feel visually meaningful — not clinical.

Habits — setup

Emotional job: Control. Adjust the system without friction.

Design intent: A clean, sortable table with one row per habit. Everything about a habit is visible — name, icon, category, weekly goal, streak, and status. The add and edit flow opens a single modal popup with five fields: name, icon grid, category, weekly goal day-pips, and an optional description. No sub-pages, no separate settings screen for habits — it all happens in one modal over the list.

Key rule: Habits is a primary navigation item — not buried in Settings. It is the most consequential configuration in the app and must be immediately accessible.

Reflect — journal

Emotional job: Stillness. A private space to think, acknowledge, and look ahead.

Design intent: The calmest screen in the app. No data, no charts, no gamification. Four cards on one scroll: Monthly Wins (green-tinted, add your achievements), Gaps & Risks (amber-tinted, note what's slipping), Notes & Journal (full-width, Lora serif textarea — borderless, feels like writing on paper), and Next Month Intentions (full-width, italic numbered list). The design uses generous whitespace and serif typography throughout.

Key rule: Reflect should feel like a private notebook, not a form. Nothing is required. The placeholder text invites rather than demands.

Typography

Plus Jakarta Sans — primary typeface for all UI text, labels, headings, navigation. Weights: 400 body, 500 medium, 600 semibold, 700 bold, 800 display. Chosen for its warmth, roundness, and confident weight range — it matches the companion tone without feeling clinical or cold.

DM Mono — secondary typeface for all data, metadata, timestamps, section numbers, labels, and Consyst attributions. Mono reinforces the OS/systems concept and creates a clear hierarchy between the human voice and the data voice.

Lora (serif) — used exclusively in the Reflect section for journal prompts, the textarea, and the intentions list. The serif creates an immediate tonal shift when the user enters Reflect — this is not a data interface anymore, it's a writing space.

06
Sitemap Evolution

How the map changed across four versions — and why each change made the app better.

Version history
Version Sections Total screens Key change
v1 Home, Today, Pulse, Journey, Reflect, System 30 First version. 5 sub-screens per section, heavy sub-navigation throughout.
v2 Home, Today, Pulse, Journey, Reflect, System 12 Sub-navigation removed. Screens consolidated. Still 6 sections.
v3 Now, Progress (Pulse+Journey), Journal, Habits 7 Major merge. Home removed, Pulse+Journey became Progress, System removed from nav.
v4 ← current Now, Pulse, Story, Habits, Reflect 6 Progress split back into Pulse (weekly) and Story (monthly). Clearer names. Reflect replaces Journal. Final structure.
Why v4 is the right structure

The decision to keep Pulse and Story as separate sections (rather than merging them into Progress as in v3) came from recognising they serve genuinely different emotional needs. Pulse is visited 2–3 times a week — it's operational. Story is visited once a month — it's reflective. Merging them into one section gave the user an awkward choice every time they visited: am I here to check the week or review the month? Separating them removes that friction and gives each its own emotional register.

The shift from "Reflect" to "Journal" in v3 and back to "Reflect" in v4 was a deliberate reversal. "Journal" is a noun — it names the container. "Reflect" is a verb — it names the action. In an app built around companion language, verbs are more powerful than nouns.

What was cut across all versions — and why
→
Onboarding flow (6 screens) — removed
A full 6-screen onboarding was designed then removed. Reason: onboarding adds friction before value. Users should reach their first meaningful screen — Now — as quickly as possible. Habits setup handles first-run configuration without a separate onboarding ceremony.
→
Home screen — removed
Home was a separate entry-point screen above the 5 nav sections. Removed because Now already does everything Home was doing — greet the user, orient them, show current state. A dedicated Home screen was a middleman with no job.
→
Dark sidebar and dark status panel — removed
Early designs used a dark ink sidebar and a dark "system status" panel. Both were removed in favour of a fully consistent warm light theme. The dark elements created tonal inconsistency — a split-personality feel. Light mode only, everywhere.
→
Sub-navigation tabs — removed from all sections
Every section once had 5 internal tabs (5×6 = 30 screens). Removing sub-navigation was the single biggest simplification. Users now need to learn only the sidebar — there is no second layer of navigation anywhere in the app.
→
System in sidebar — moved to gear icon
System/Settings was initially a primary nav item (section 05). Moved to a gear icon at the sidebar footer. Settings are not something users visit on a daily or weekly basis — they shouldn't occupy the same visual weight as Today or Pulse.
→
Life timeline, year in review, streak board as standalone screens — removed
These were initially separate navigable screens. All converted to inline widgets within Story. The information is the same — it just lives on a scroll rather than behind a tab click.
07
Key Design Decisions

The significant choices made during design sessions — what was decided, what was considered, and why.

Decision 01
Now opens on launch — no home screen
The app opens directly to Now (the dashboard) every session. There is no intermediate home or splash screen.
Now already orients the user — date, today's progress, streak, week state. A separate home would be a middleman with nothing to add.
Decision 02
Pulse only allows checking — not adding
In Pulse, users can check and uncheck weekly habit completions. They cannot add new habits, change goals, or edit any other data from this view.
Keeps the weekly view focused on assessment, not configuration. Adding habits belongs in Habits. Mixing the two creates cognitive friction during a routine check-in.
Decision 03
Story is designed to feel magical
The monthly view uses richer visual components, warmer language, and a layout that rewards scrolling. The heatmap, goal vs actual bars, and summary badges are designed to make a month of data feel like a narrative.
Users should be excited to visit Story — not afraid of it. The monthly view is the reward for daily consistency. It should feel that way.
Decision 04
Habits is primary nav, not settings
Habits lives in the main sidebar at the same level as Now, Pulse, and Story — not buried in a Settings menu.
Adding and editing habits is the most consequential configuration in the app. Burying it in Settings creates friction for the most important action a new user needs to take.
Decision 05
Habits use a modal, not a sub-page
Adding and editing habits opens a modal overlay on the habits list — not a separate page. The modal closes back to the list.
A modal keeps the context — the user can see the list behind the overlay and immediately see their change reflected when they close it. A sub-page loses that context.
Decision 06
Reflect uses serif typography
The Reflect section uses Lora serif for the journal textarea, prompts, and intentions — the only place in the app where the typeface changes from Plus Jakarta Sans.
A typographic shift signals an emotional shift. When you see serif text in Consyst, you know you've entered a different kind of space — quieter, more personal.
Decision 07
Light mode only — no dark mode
The entire application uses one warm light theme. There is no dark mode, no toggle, no system preference detection.
Consistency in tone reinforces the feeling that everything belongs to the same unified system. A single theme is a design statement — not an oversight.
Decision 08
Web-first, not mobile-first
Consyst is designed as a web application with responsive behavior for mobile screens.
A web-first approach gives the design room to breathe — proper sidebars, data-rich widgets, multi-column layouts. The desktop viewport is where the OS metaphor is most powerful.
Decision 09
Consyst speaks — in cards, not notifications
The "Consyst" observation widget appears in Now and is referenced in Pulse and Story. It delivers one contextual observation at a time, signed with the Consyst logo.
The companion relationship requires Consyst to have a voice. But that voice must feel earned — surfaced from real data, delivered quietly, never as a push notification or gamification badge.
Decision 10
Grade messages are forward-looking, not backward
The grade card in Pulse always frames the grade in terms of what's still possible — never in terms of what was missed.
"You're doing well — one strong finish away from an A" is more useful than "you scored 78%." The first statement tells you what to do next. The second just describes where you are.

Q1
First-time user flow — no onboarding
Onboarding was removed. The decision was: take the user directly to Now, then prompt them to add habits if none exist. The exact first-run experience (empty states, prompts, initial habits setup) has not been designed.
Q2
Empty states
What does Now look like with no habits? What does Pulse look like in the first week? What does Story look like in the first month? Empty states need companion-voice copy and gentle prompts to get started.

Mobile responsive behavior
The sidebar collapses on mobile. The score card row stacks vertically. The habit × day grid in Pulse requires horizontal scrolling on small screens. Breakpoints and mobile layout adaptations have not been formally defined.

The "Consyst" widget in Now surfaces one observation at a time. The logic behind what triggers an observation — thresholds, pattern detection, note analysis — has not been defined.

Landing & Sign In Pages

The two pages that exist outside the app — the first impression and the door back in.

Design philosophy — marketing pages

The landing page has one job: make someone feel something before they read anything. Consyst is not competing on features — it's competing on philosophy. The person landing here has probably tried habit trackers before and abandoned them. The page must speak to that skepticism directly and honestly, not lead with a feature checklist.

The sign in page is a door — the moment before stepping back into your system. It should feel quiet and confident, carry the brand without noise, and complete in as few interactions as possible.

Aesthetic direction: editorial minimalism with conviction. Large type, deliberate whitespace, the product shown with pride. Think the editorial confidence of a quality print magazine — not a startup landing page template.

Create account: first + last name (two columns), email, password with a 4-bar live strength indicator, "Start your system →" submit button, Google sign-up option. A "← consyst.io" back link sits fixed in the top-right corner.
One URL for both sign in and create account removes the friction of navigating between pages. The tab switcher also updates the headline and subtitle dynamically — "Sign in to Consyst" becomes "Start your system" without a page reload.
Submit behavior
Immediate feedback on click
The submit button changes state on click without waiting for a server response: "Enter Consyst" → "Signing in…" (teal background) → "Welcome back ✓" after 1.2s. Create account: "Start your system" → "Setting up…" → "System ready ✓". The button never goes disabled and grey — it always communicates forward momentum.
Companion language extends to micro-interactions. "Welcome back ✓" and "System ready ✓" are in the Consyst voice — warm, confident, personal. Not "Success" or "Done."
Password strength
Four bars, colour-coded
Appears only on the Create account tab. Four thin bars below the password input, updating live as the user types. Empty = chalk. 4+ chars = one coral bar. 8+ = two amber bars. 12+ = three teal bars. 16+ = four teal bars. No text labels, no "weak/strong" words — the color and count communicate clearly without moralizing.
The four bars reference the Pulse Stack logo subconsciously — four bars rising from left to right, gaining height and changing from warm to cool. Functional and on-brand simultaneously.

Settings Screen

The back panel of the OS — one scrollable screen, no sub-navigation, accessed via the gear icon at the sidebar footer.

Design intent

Settings is visited rarely and deliberately. The design feels like opening the preferences panel of software you trust completely — precise, clean, nothing surprising. No tabs, no internal navigation, no wizards. One scroll reveals everything. The "Save changes" button in the top bar gives immediate feedback: it becomes "Saved ✓" in teal on click, then resets after 1.8 seconds — keeping the companion voice present even in the most functional part of the app.

Five sections — in order top to bottom
S1
Account — name, email, password
Three form rows: name (how Consyst addresses you), email (used to sign in), password (with last-changed date as the sub-label). No surprises, no extra fields. The name field is the same name used throughout the app in greetings and milestones.
S2
Reminders & rhythm — four toggles, two time selectors
Daily check-in reminder (toggle + time selector). Weekly review reminder (toggle + day selector + time selector). Consyst observations (toggle). Milestone alerts (toggle). All toggles are interactive — click to flip between on (teal) and off (border-grey). Time selectors are always visible to show current settings at a glance.
S3
Your Consyst profile — stats + system history
Four stat cards: days running (teal), best streak (amber), active habits (purple), average score (blue). Below the cards: a system history log showing every habit change ever made — dated entries recording additions, goal adjustments, and archiving. This turns Settings from a utility screen into a quiet record of the user's journey. The history is read-only — a permanent log, not editable.
S4
Data & export — three stats, four export options
Three data stats (days of data, check-in records, notes & entries) give transparency about what Consyst holds. Four export options: CSV (all habit data), PDF (monthly report card), TXT (all journal entries as plain text), ZIP (everything — CSV, all PDFs, TXT, full JSON backup). The ZIP "Export all" button uses ink-black to signal it is the most complete action. A teal-tinted privacy note confirms data is never shared or sold.
S5
Danger zone — at the bottom, visually distinct
Red border, red header background, red title. Two buttons: Reset all data and Delete account. Both trigger a browser confirmation dialog before executing — genuine friction for irreversible actions. The section is last, visually subordinate to everything above it.
Key design decisions — Settings
Decision 01
One scroll, no tabs
All setting areas live on one scrollable page with clear section cards. No tabs, no sub-pages.
The user visits Settings to do something specific. Every additional navigation layer is friction. A single scroll makes everything immediately findable.
Decision 02
Profile stats live in Settings
Days running, best streak, active habits, and average score appear in the Profile section — not as persistent sidebar elements.
These numbers are context, not action. Alongside the system history they make Settings feel like a record of the journey, not just a preferences panel.
Decision 03
System history is read-only
The habit change log is a permanent, read-only record. Users cannot edit or delete entries.
The history is a form of memory — it shows how the system has evolved. Making it editable would undermine its value as a truthful record.
Decision 04
Danger zone requires confirmation
Reset and Delete trigger a browser confirm() dialog. Red styling communicates severity; the dialog enforces intentionality.
Two layers of friction for the most irreversible action in the app — the color signals danger, the dialog demands deliberate consent.

Empty States — Day 1

What every screen looks like when a new user arrives with no data, no habits, and no history. The companion speaks first on every screen.

Design philosophy — empty states

Empty states are harder than full states. When there is no data, the interface must do two things simultaneously: explain what this screen is for, and invite the user to begin. Done wrong it feels like a blank wall. Done right it feels like an open door.

The principle applied across all five empty states: the companion speaks first. Every empty state is Consyst making its first meaningful statement to this specific user. Not "No data found." Not "Get started." Something considered and personal. Each screen also shows a ghost or preview of what it will look like when populated — the user can see the shape of what they are building toward.

Empty states are not error states. They are beginning states — the first page of the story. The tone is warm, the direction is clear, and the companion's voice is present from the very first moment.

Now — Day 1 empty state

Situation: New user has signed in. No habits added yet. The dashboard has nothing to show.

Design approach: Ghost score cards — the four card outlines are present at low opacity with dashed borders, showing the user the shape of what will fill in. Ghost widget skeletons below. In the centre, a teal seedling icon, the eyebrow "Day 1 · Nothing tracked yet", the headline "Your dashboard fills up as you show up.", and a Lora italic body explaining that score cards and insights appear once habits are running. The CTA is "Add your first habit →" in teal — the most direct possible action. A Consyst note at the bottom: "Start with 2 or 3 habits — not ten. The system earns your trust through consistency, not ambition."

Key decision: The top bar greeting changes on Day 1. Instead of "Good morning, Alex." with the date, it reads: "Your system is ready — let's build it." with "Day 1" on the right. This is the only day the greeting changes from the standard format — it marks the beginning without ceremony.

Ghost elements are shown at 30–35% opacity with dashed borders. They communicate "this is what you will see" without being distracting or confusing. The user understands immediately that data will fill these shapes.

Pulse — Day 1 empty state

Situation: User visits Pulse in their first week with no check-ins logged yet, or before adding any habits.

Design approach: A ghost version of the habit × day grid — dashed outlines where the checkboxes will be, with the amber "today" column slightly more visible to orient the user. The headline: "Your weekly rhythm starts today." The body explains Pulse shows each week habit by habit, day by day, and that the grid fills in as they check off habits in Now. Two CTAs: "Go check in today →" (amber primary) and "or add your habits first" (text secondary). The Consyst note teaches the user how to use the section: "Pulse is most useful mid-week — when there's still time to course-correct. Come back Wednesday or Thursday."

Key decision: Pulse's empty state is the only one with two CTAs — because there are genuinely two valid starting points depending on whether the user has habits yet. The secondary CTA is a text link, not a button, to maintain visual hierarchy.

Story — Day 1 empty state

Situation: User visits Story on Day 1 or early in Month 1 with no meaningful data to show.

Design approach: The most visual of the five empty states. A row of six bars representing months — March is a small teal-filled block with a striped texture (representing the current, in-progress month). April through August are empty dashed outlines, each one taller than the last — a rising arc of future months yet to be written. Below the bars: "YOUR ARC — IT BUILDS FROM HERE" in tiny mono caps. The month picker in the top bar is shown at low opacity. The headline: "Every great story starts on page one." The Lora body: "Story shows you the arc — heatmaps, trends, your best habits and your growing ones. Come back at the end of the month and see what you built." The Consyst note sets time expectations honestly: "Story gets richer with time. After one month you'll see trends you couldn't have noticed yourself. After three, you'll know your system deeply."

Key decision: The rising bars illustration is the emotional centrepiece. It visualises the potential of the system — the arc you haven't written yet — without overpromising. The bars are empty dashed outlines, not filled with hypothetical data.

Habits — Day 1 empty state

Situation: User arrives at Habits with no habits configured. This is the most active empty state — the user must do something here.

Design approach: Deliberately the most action-oriented of the five. No ghost elements, no patience required. A direct question as the headline: "What dimensions of your life do you want to track?" Below: a grid of suggestion chips — Exercise, Meditation, Reading, Sleep 7+, Running, Journaling, Hydration, + Something else — all hoverable and tappable. These are suggestions, not a forced onboarding form. The user can ignore them and click "+ Add habit" directly. The primary CTA is "Add your first habit →" in purple. The "+ Add habit" button in the top bar is also always visible. The Consyst note delivers the key philosophy upfront: "Be honest about your capacity. A 3× per week goal you keep is worth more than a 7× goal you break."

Key decision: Suggestion chips instead of a blank input field. Starting from zero with a blank input creates friction and decision paralysis. Chips give the user momentum — they feel closer to starting if they can see familiar options already named. The chips are not a form; selecting one still opens the full add-habit modal so the user can customise everything.

Habits is the only empty state where the top bar CTA ("+ Add habit") is active and visible. On all other empty screens, the top bar is minimal. Habits needs to signal clearly that action is possible from multiple points on the screen.

Reflect — Day 1 empty state

Situation: User opens Reflect on Day 1 with nothing written yet — no wins, no gaps, no journal entries, no intentions.

Design approach: The calmest of the five empty states, matching the section's overall tone. Five ruled lines like a blank notebook page — the first line in a faint teal, the rest in the standard border colour. No ghost cards, no skeleton UI. The headline is quiet: "This is your space. No rules." The body is in Lora italic — a quote-like statement: "You can start a win today, note something you want to pay attention to, or just write what's on your mind. There's no wrong way to use this." Three contextual entry points replace a single CTA: Record a win (teal hover), Write a note (blue hover), Set a monthly intention (purple hover). Each card has a name and a one-line description. The Consyst note is honest about timing: "Reflect works best at the end of a month — when you have something to look back on. But you can write here any time."

Key decision: Three entry points instead of one CTA. Reflect serves different purposes at different moments — a win is different from a note is different from an intention. Forcing the user through one button loses that nuance. The three-option layout respects that they might be here for any of those reasons.

Empty state design decisions — cross-cutting
Decision 01
Companion speaks on every empty screen
Every empty state ends with a Consyst-signed observation — a small card with the logo and one piece of genuine guidance specific to that screen.
The companion relationship begins on Day 1, not after data accumulates. The Consyst note on each empty screen is the system's first act of being useful — before there is any data to analyse.
Decision 02
Ghost elements show the future shape
Now and Pulse show ghost versions of their primary UI elements — score cards and the habit grid — at low opacity with dashed borders.
Ghost elements answer the question "what will this look like?" without requiring explanation. The user understands immediately that data will fill these shapes. It also makes the screen feel less empty — there is structure here, waiting to be populated.
Decision 03
Day 1 greeting is different — once only
The Now top bar greeting changes on Day 1 to "Your system is ready — let's build it." Every subsequent day it returns to the standard "Good morning, Alex."
Day 1 deserves acknowledgement without ceremony. One changed line in the top bar marks the beginning. The standard greeting returns immediately on Day 2 — the system is already running, no ongoing fanfare.
Decision 04
No onboarding flow — Habits is the entry point
There is no separate onboarding wizard or welcome sequence. The user lands on Now (empty state), which directs them to Habits to add their first habit.
Onboarding flows create friction before value. The empty state of Now acts as the onboarding — it explains the situation, shows what's missing, and provides a direct path to fix it. The user is in the real app from the first second.
Decision 05
Each empty state teaches the section's purpose
The Consyst note on each empty screen explains not just what to do but when the section is most useful — e.g. "Pulse is most useful mid-week", "Story gets richer after one month."
New users don't know the app's rhythm yet. The empty states are the best moment to teach it — when the user is curious and paying attention, before habits and data create urgency.
Decision 06
Habits suggests, never forces
The Habits empty state shows suggestion chips but none are pre-selected. The user can click any chip to open the add modal pre-filled, or ignore them entirely and click "+ Add habit."
Forcing habit selection during onboarding was removed from the design explicitly. The suggestion chips bring back the value of that idea — reducing blank-slate paralysis — without creating a mandatory step. The user remains in control.

Tech Stack

The confirmed technology decisions for Consyst — web app first, mobile app as a fast follow-up. Optimised for a Claude Code development workflow, affordable hosting, and a fully TypeScript codebase.

Key constraints that drove the decisions
C1
Claude Code is writing the code
The stack is optimised for what Claude Code writes best — TypeScript, React, and well-documented ecosystems. Type safety means Claude Code catches its own errors as it writes. One language across the entire stack means Claude Code holds full context in one session.
C2
Web app now, mobile as a fast follow-up
The web app is the primary surface. Mobile should reuse as much as possible — same database, same auth, same API, same TypeScript business logic. A complete rewrite for mobile is not acceptable.
C3
Affordable but not free-tier
Free tiers have sleeping servers, row limits, and bandwidth caps that create a bad user experience for a daily-use app. The target is a production-grade setup under $55/month.
C4
The data model is relational and PostgreSQL-native
The schema we designed uses check constraints, triggers, JSONB columns, partial indexes, and versioned goal rows. PostgreSQL is the only database that runs it without compromise.
C5
No subscription logic — no billing infrastructure needed
Consyst is a personal tool, potentially shared freely. No Stripe, no billing tables, no plan-based feature gating. The stack does not include any payment infrastructure.

Development workflow — Claude Code

With Claude Code as the developer, the day-to-day workflow is:

01
Describe the feature
Give Claude Code the feature description, referencing the design document for the screen and the data model document for the schema. Both documents are the source of truth — Claude Code reads them, not you.
02
Claude Code writes the Prisma migration (if needed)
Any schema changes are written as Prisma migration files. Claude Code runs: npx prisma migrate dev. The migration is versioned in the repository — the full schema history is tracked.
03
Claude Code writes the API route
Next.js API routes (in /app/api/) handle custom business logic — the week score calculation, streak computation, milestone detection. These are TypeScript functions that call Prisma and return typed responses.
04
Claude Code writes the React component
UI components are written in TypeScript/React, styled with Tailwind CSS, and match the designs in the design document exactly. Claude Code has the full visual spec to reference.
05
Push to GitHub → Vercel auto-deploys
Every push to the main branch triggers a Vercel deployment. Changes are live in ~30 seconds. Preview deployments on every branch let you review before merging.
Mobile strategy — PWA first, React Native second

Step 1 — PWA (immediate, zero extra cost): The Next.js web app is configured as a Progressive Web App from the start. A manifest.json and service worker — roughly 20 lines of configuration — make the app installable on iOS and Android home screens. It behaves like a native app for everyday use: opens full-screen, caches recent data for offline viewing. This is done alongside the initial web build.

Step 2 — React Native + Expo (when native is needed): When the PWA experience is insufficient — push notifications, app store presence, deeper device integration — React Native with Expo is the natural extension. The Supabase JavaScript client (@supabase/supabase-js) is identical in React Native. The same database, the same auth session, the same API routes are called. Claude Code writes mobile screens in React Native using the same patterns it already knows from the web app. No second backend, no second database, no second auth system.

The mobile path is additive, not duplicative. Everything built for the web app is reused. The Supabase project stays the same. The TypeScript business logic stays the same. Only the UI layer changes — React components become React Native components, which Claude Code handles directly.

What was considered and not chosen
—
Heroku — evaluated, not chosen
Heroku is a solid PaaS but has three problems for this use case: (1) cheap dynos sleep after 30 minutes of inactivity — bad for a daily-use app, (2) no built-in auth — Google OAuth requires weeks of additional work or another paid service, (3) similar pricing to Supabase + Vercel but significantly less included. Heroku is the right choice if the backend is Python — it is not the right choice for a TypeScript/Next.js app.
—
Railway — evaluated, not chosen
Railway is a strong alternative to Heroku for deploying custom backends. More affordable and doesn't sleep. But like Heroku, it has no built-in auth, no auto-generated API, and no mobile SDK. The extra work to replicate what Supabase includes out of the box isn't justified for this use case.
—
Firebase — not evaluated
Firebase uses a document database (Firestore), not a relational one. Our data model is deeply relational — versioned goals, check constraints, complex joins. Migrating the schema to a document model would require significant architectural compromises. Not considered.
—
Separate backend (FastAPI, Express) — not chosen
A separate backend server adds a second deployment, second codebase, and second set of infrastructure to manage. Next.js API routes handle all the custom logic we need — streak calculations, milestone detection, observation engine — without a separate service. The system stays as simple as possible.
—
SvelteKit / Remix — not chosen
Both are strong frameworks. SvelteKit has less Claude Code familiarity. Remix has a smaller ecosystem. Next.js is the highest-confidence choice for Claude Code output quality — the largest TypeScript web framework by usage and documentation coverage.
